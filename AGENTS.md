# Repository Guidelines

## Project Structure & Module Organization
The tracked GCC sources stay under `gcc/`. Core compiler work happens in `gcc/gcc`, while Fortran runtime updates live in `gcc/libgfortran` and supporting math libraries such as `gcc/libquadmath`. Keep new test cases under `gcc/gcc/testsuite/gfortran.dg/` using descriptive `*.f90` filenames. Keep minimal reproducers in `bugs/`. `gcc-build/` is the out-of-tree build tree generated by the bootstrap script—treat it as disposable output and never hand-edit files there.
- All git operations (commit, branch, reset, status) happen inside `gcc/` to keep repo history clean.
- All compiler builds/tests run in `gcc-build/` using `make -C gcc-build ... -j32`.
- All reproducers and investigation docs live in `bugs/`; update `bugs/ALLOCATABLE_DEEPCOPY_PLAYBOOK.md` whenever work progresses.


## Build, Test, and Development Commands
- `./bootstrap.sh` reconfigures `gcc-build/` with the project defaults (`--enable-languages=fortran`, checking enabled, debug flags). Re-run after pulling configure-time changes.
- `make -C gcc-build -j$(nproc) all-gfortran` builds the compiler, runtime, and support libraries with parallel jobs.
- `make -C gcc-build check-gfortran RUNTESTFLAGS="--target_board=unix/-O0"` runs the Fortran DejaGNU suite; adjust `RUNTESTFLAGS` for targeted scenarios.
- `python3 gcc/contrib/test_summary gcc-build/gcc/testsuite/*.sum` condenses test results and must accompany any test discussion.
- `make -C gcc-build install-gfortran DESTDIR=$PWD/stage` stages an installable tree for manual validation.

## Coding Style & Naming Conventions
Mirror upstream GNU conventions: two-space indentation for C/C++ sources, braces on their own lines, and 80-column limits unless a surrounding file states otherwise. For Fortran code, use four spaces, 88-column wrapping, `implicit none`, and `use, intrinsic :: iso_fortran_env, only: dp => real64`. Prefer `gfc_` prefixes for new gfortran helpers and follow existing namespace patterns (`*_t` for derived types, `gfc_*` or `gfortran_*` for functions). Run `python3 gcc/contrib/check_GNU_style.py <path>` before sending patches and fix every reported issue.

## Testing Guidelines
Keep new tests minimal and self-checking using `dg-do run` or `dg-do compile` directives. Group related scenarios into the same `.exp` entry to avoid slow harness lookups. When triaging regressions, archive the failing source in `bugs/` and reference it from the commit message. Target at least one positive and one negative test for each new feature flag. Always attach the relevant `.sum` excerpt or `test_summary` output when sharing results.

## Commit & Pull Request Guidelines
Craft small, reviewable commits scoped to a single subsystem; use messages in the form `component: imperative summary` (e.g., `gfortran: fix polymorphic deep copy`). Stage files explicitly with `git add path/to/file`. Before opening a PR, ensure `make -C gcc-build check-gfortran` passes and paste the summarized results. PRs should link the motivating Bugzilla ID (if any), describe the root cause, detail the fix, and note follow-up work. Screenshots are unnecessary; attach logs instead. Merge only after reviewers acknowledge and CI mirrors your local success.
